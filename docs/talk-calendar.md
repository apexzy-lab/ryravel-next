# Ryravel curator-call calendar

`/talk` is a first-party 25-minute Google Meet booking flow. It does **not** book a journey or charge a traveller. The page remains unlinked and `noindex` until an owner authorizes the calendar connection and a live booking test succeeds.

## Connection required before launch

1. `ryravelinc@gmail.com` owns the curator-call calendar. The approved schedule is weekdays, 10:00–16:30 in `TALK_HOST_TIMEZONE` (default `Africa/Lagos`), 25-minute calls at 30-minute starts, with a 10-minute buffer, 24-hour notice, and a 45-day booking window. Client-facing booking emails must come from `curator@ryravel.com`, not Gmail.
2. In a Google Cloud project controlled by Ryravel, enable Google Calendar API and create a Web OAuth client. Authorize the calendar-owning Google user for offline Calendar access. Do not paste the client secret or refresh token into chat or commit them to Git.
3. Set the following Worker secrets: `TALK_GOOGLE_CLIENT_ID`, `TALK_GOOGLE_CLIENT_SECRET`, `TALK_GOOGLE_REFRESH_TOKEN`, `TALK_GOOGLE_CALENDAR_ID` (normally `ryravelinc@gmail.com`). Set `TALK_HOST_TIMEZONE` as a Worker variable only if the calendar is not based in Lagos.
4. Verify **ryravel.com** (the root domain, not only `updates.ryravel.com`) for sending with the current Resend account, including SPF/DKIM and any needed DMARC alignment. The existing `RESEND_API_KEY` is used. Only after a real test email from `Ryravel Curator <curator@ryravel.com>` arrives with its calendar attachment may `TALK_EMAIL_SENDER_READY=true` be set in the Worker. This flag is deliberately absent by default.
5. `drizzle/0006_talk_bookings.sql` was applied to the production D1 database before the first code deployment. The live route fails closed without the connection values and verified-sender flag.
6. Test availability, a real calendar conflict, one booking to an owner-controlled inbox, the Ryravel sender and calendar attachment, the Meet link, and the curator’s view. Only then link `/talk` from the request flow and allow indexing.

The Calendar API’s free/busy response controls visible slots. On confirmation the site inserts a D1 reservation, rechecks Google, creates a unique calendar event **without a Google guest attendee**, waits for its Meet link, and confirms the UI only after Google returns an event ID and Meet link. Because Google invitations would expose the personal Gmail organizer, no Google invitation is sent. A durable outbox job sends one branded confirmation and `.ics` calendar file from `curator@ryravel.com` using Resend. A separate service-only `ryravel_call_booked` signal informs GTMCR without triggering either existing request-acknowledgement automation; GTMCR list/pipeline rules for this event require separate configuration. A failed or ambiguous create attempt keeps the slot reserved for operator reconciliation and is included in the operating alert after five minutes. Authenticated staff can inspect the most recent records at `/api/admin/talk/bookings`. Because the guest is not a Google attendee, Google edits do not automatically update their calendar file; the curator must send any change from the Ryravel address.

The optional brief is placed in the curator’s private Google event, not the outbound email or calendar file; it does not grant marketing permission. This first release does not offer self-service cancellation or rescheduling. Guests reply to the confirmation or email `curator@ryravel.com` with the `RT-` reference. Do not advertise self-service management until it exists.
